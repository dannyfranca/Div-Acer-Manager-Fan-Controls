## Sensors and initial temperature policy

Current read-only observation: `coretemp` exists; `nvidia-smi --query-gpu=name,temperature.gpu --format=csv,noheader` identifies RTX 3070 Laptop GPU but reports **`[GPU requires reset]`** instead of temperature. That is a blocking GPU-health observation. Reboot/recovery and re-observation belong to installation qualification; do not issue a live GPU reset as a planning step. CPU-only sensing is insufficient while GPU workload can run. If healthy GPU temperature cannot be obtained, leave fans in firmware Auto and investigate that failure before claiming custom curves work.

After the driver passes hardware checks:

1. Record the Acer hwmon `name`, real device path/driver, both fan labels, `fanN_input`, `pwmN`, and `pwmN_enable`; do not persist `hwmonN` indices. Prove CPU/GPU fan mapping with isolated channel tests, not label guesses.
2. Identify CPU package temperature from `coretemp` and GPU core temperature from NVIDIA's working sensor backend. Compare the UI to simultaneous read-only sensor readings under CPU-only, GPU-only, and combined load. Record CoolerControl device UID/channel names after discovery.
3. Create two **Graph** profiles with component-specific temperature-to-duty curves. Combine using a **Mix → Max** profile, applied to both fans initially. Maximum demand allows either hot component to request cooling without averaging away the hotter component; separate fan tuning is optional after shared-path behavior is measured. Each curve must reach 100% by its validated high-temperature point and stay at 100% through 100°C, so missing-sensor substitution cannot produce a low duty.
4. Balanced starting *policy*: no fan-stop; retain a margin above each observed stable spinning duty; choose points from firmware-Auto idle/load observations and the validation ticket's component limits; prioritize thermal margin over quietness initially. Do not invent a PT315-53 minimum duty, RPM, throttle temperature, or GPU maximum. Start with unfiltered temperatures and a Standard function using **only-downward hysteresis**. Suggested tunable software starting values: 2°C downward threshold and 5s downward delay, upward maximum step 100 percentage points, downward maximum step 5 points, minimum step 1 point; these are a proposal, not thermal qualification. Retain 1s polling. Validate upward response and sensor-loss response before enabling at boot.
5. Keep automatic calibration/fan-stop searches off for first qualification: generic sweeps can test duties not yet proven on this firmware. Hardware checks establish the usable duty floor first. Export/back up accepted daemon configuration from `/etc/coolercontrol/` after assignments; record exact points, function values, and device identities in installation evidence.

The release supports Graph/Mix/Max and Standard hysteresis; its default polling is 1s and `apply_on_boot=true`. Initially set `apply_on_boot=false` while inspecting devices and creating profiles; change to true only after assignments and restart behavior pass. [Profiles](https://docs.coolercontrol.org/cooling/profiles), [functions](https://docs.coolercontrol.org/cooling/functions), [Mix implementation](https://gitlab.com/coolercontrol/coolercontrol/-/blob/e041bffd7d27495b947d8ea5df3b9085ef314d64/coolercontrold/daemon/src/engine/commanders/mix.rs), [configuration defaults](https://gitlab.com/coolercontrol/coolercontrol/-/blob/e041bffd7d27495b947d8ea5df3b9085ef314d64/coolercontrold/daemon/src/config.rs).

Existing failsafe handling substitutes 100°C for sufficiently stale known sensors after the threshold of eight missing ticks; missing graph sources also have emergency-temperature handling. Standard upward response must remain unsmoothed. A Mix missing a member's calculated output skips that update; it does not silently average only surviving members. Therefore qualify both source-loss paths, including absent-at-start and loss-after-start. New device-health reporting exposes missing/stale/failsafe states and firmware overrides; observe it and journal errors during testing. It is not independent proof of RPM or firmware acceptance. [Failsafe](https://gitlab.com/coolercontrol/coolercontrol/-/blob/e041bffd7d27495b947d8ea5df3b9085ef314d64/coolercontrold/daemon/src/repositories/failsafe.rs), [function source handling](https://gitlab.com/coolercontrol/coolercontrol/-/blob/e041bffd7d27495b947d8ea5df3b9085ef314d64/coolercontrold/daemon/src/engine/processors/functions.rs), [device health](https://gitlab.com/coolercontrol/coolercontrol/-/blob/e041bffd7d27495b947d8ea5df3b9085ef314d64/coolercontrold/daemon/src/device_health.rs).

## Finite integration to implement later

Package the following small integration alongside the driver adaptation. This is an artifact contract, not installed or tested unit code.

| Artifact | Required contract |
|---|---|
| `/usr/lib/pt31553-fan-control/session` | Bounded helper commands `guard`, `prepare-start`, `restore-auto`, `prepare-sleep`, `finish-sleep`, `recover`; injectable sysfs/root/command interface for fixtures. Validates exact DMI/device identity; discovers hwmon by identity; serializes its own transitions; structured journal outcomes. |
| `/etc/pt31553-fan-control/device.toml` | Validated DMI, driver/device identity, two channel identities, selected CPU/GPU sensor identity and admissible fresh-reading checks. No unstable hwmon index. |
| `coolercontrold.service.d/pt31553.conf` | `ExecCondition=... guard`; `ExecStartPre=... prepare-start`; `ExecStopPost=... restore-auto`. Preserve stock notify/watchdog/restart. Use `TimeoutAbortSec=5` so watchdog crash-dump handling cannot add a long uncontrolled delay; measure total stop/recovery time, not merely the30s watchdog. |
| `pt31553-fan-sleep.service` | `Type=oneshot`, `RemainAfterExit=yes`, `StopWhenUnneeded=yes`; prepare/finish lifecycle with bounded timeout. Marker created before stopping controller; remembers whether controller was active. |
| Four sleep-engine drop-ins | For `systemd-suspend`, `systemd-hibernate`, `systemd-hybrid-sleep`, `systemd-suspend-then-hibernate`: `Requires=pt31553-fan-sleep.service` and `After=pt31553-fan-sleep.service`. This makes failed preparation stop the actual sleep job. |
| Fixture tests and install manifest | Verify helper failures, unit dependency ordering, package file ownership/removal, no wrong-device writes, second fan attempted after first fails, startup refusal on failed restoration, explicit recovery, and clean unsupported-boot skips versus endpoint loss after ownership. |

`prepare-start` must establish both fan enables as **2 with readback**, then verify fresh required sensors and the qualified driver identity before daemon execution. The daemon therefore saves Auto as its reset default. Avoid any competing fan controller or arbitrary sysfs writers. `guard` skips startup while a sleep or restoration-failure latch exists; failed restoration remains latched until explicit inspection/recovery. A skip must not produce an automatic restart storm. A start failure must still attempt Auto restoration for every discovered qualified channel.

**Ownership and unsupported boots:** `guard` must distinguish a clean stock/LTS boot from failure during a candidate session. With no candidate ownership record for the current boot and no matching qualified driver, return the normal skip code `1`, log “unsupported stock/recovery kernel; firmware retains ownership,” and perform no fan writes. Do not create a missing-device fault or restart storm. Do not infer firmware Auto from absent files; this result means the custom controller never acquired ownership. Before the first candidate control write, `prepare-start` records a boot-ID-scoped ownership record containing the qualified driver and both channel identities. That record survives daemon crashes/restarts and is released only after successful Auto verification. Missing endpoints after acquisition are a restoration fault, even if later discovery resembles an unsupported boot; retain the record and fault latch. Never erase prior ownership merely because a new discovery fails.

**systemd cleanup detail:** the installed `systemd.service(5)` manual and upstream manual source confirm that an `ExecCondition` exit1–254 skips startup without marking the unit failed, **but still invokes `ExecStopPost`**. Accordingly `restore-auto` must first inspect boot-scoped ownership: with none, it returns success without discovering/writing absent stock nodes; with ownership, it attempts complete restoration, regardless of whether the current invocation reached `ExecStart`. A condition skip must not accidentally clear an existing fault latch. Existing sleep/fault markers may make `guard` skip while an older ownership record remains, so cleanup must be idempotent and must not release a fault latch automatically. [systemd service manual source](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml)

**Explicit recovery:** `sudo /usr/lib/pt31553-fan-control/session recover` is the only normal command that clears a restoration-failure latch. Require CoolerControl fully stopped with no pending start/restart, exclude concurrent session transitions, and refuse recovery while a sleep transition is active. Revalidate the qualified device identity; attempt Auto2 on both fans and read both back. Clear the fault latch and any satisfied ownership record only when every required verification succeeds; retain both on any failure, including missing endpoints. Log the full outcome and **do not start CoolerControl**. The subsequent explicit start separately checks fresh sensors and qualification. Recovery does not bypass the unsupported-driver check or “clear” a failure by deleting state files.

Required fixtures: stock/LTS boot with no ownership and no Acer nodes (`ExecCondition` skips; post-stop no-op; no writes/fault/restart); candidate partially acquired then missing either/both nodes (post-stop latches fault and tries remaining qualified fan); skip caused by existing fault preserves it; successful stop releases ownership; recovery refuses active/starting controller or sleep, failed recovery retains latch, successful recovery verifies both Auto modes and leaves daemon stopped. Cover failed `prepare-start` after ownership registration so its post-stop recovery cannot be skipped.

`restore-auto` runs **after the daemon is stopped**, including SIGKILL and watchdog termination, with no racing curve writes. Discover afresh, write sysfs **2** to each qualified fan's `pwmN_enable`, then read both back. Attempt both even if the first fails. Nonzero result, journal diagnostics, and a root-owned `/run/pt31553-fan-control/` fault latch on any missing channel, write/read failure, or mode mismatch. Normal restart may continue only after successful restoration and fresh-sensor startup checks. Successful `tee`/process exit alone is insufficient. `0` means maximum/Turbo, `1` Custom, `2` firmware Auto; raw Acer firmware enums are different.

**Clean stock/recovery sleep:** when there is no qualified candidate, no current-boot ownership record, and no restoration fault, sleep preparation succeeds without fan writes or requiring absent PWM endpoints. Its finish action must not start CoolerControl. This is a clean unsupported-boot branch, not evidence that missing endpoints prove Auto. Existing ownership, a restoration fault, or endpoints lost after acquisition must never take this branch; retain the fault and block sleep until verified recovery. Add fixtures for all four sleep engines on clean stock/LTS boots, plus missing endpoints with prior ownership and an existing fault.

`prepare-sleep` otherwise records prior activity, creates the sleep marker, synchronously stops CoolerControl, waits for stop/post-stop completion, and independently verifies both Auto modes before succeeding. All actual sleep engine units depend on this success; do not use a best-effort `/usr/lib/systemd/system-sleep` script whose failure can be ignored. This ordering waits before the sleep engine starts, avoiding dependence on a short logind notification/inhibitor timeout. Add a finite overall preparation timeout; failure must leave the controller stopped, attempt Auto restoration, and abort sleep, with a visible failed job. If any restoration failed, keep the fault latch; do not report verified Auto.

Once the sleep engine is finished and no longer needs the preparation unit, its finish action clears the sleep marker and restarts **only a previously active** controller. Restart goes through the same fresh-device/fresh-sensor/Auto checks. A failed or cancelled sleep attempt must also clear a stale sleep marker safely; define `ExecStopPost` cleanup for oneshot-start failure because `ExecStop` alone does not cover it. Do not clear a restoration-failure latch. Unit fixtures must check all four sleep variants, cancelled/failed preparation, failed resume sensor discovery, and controller disabled before sleep. Dependencies must be verified using `systemd-analyze verify` and a simulated lifecycle before installation. [systemd service semantics](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html), [unit dependency semantics](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html). Also inspected this host's `/usr/lib/systemd/system/sleep.target` and `systemd-suspend.service`; the latter requires/orders after `sleep.target`.

No new continuous controller, custom curve engine, or separate watchdog daemon is needed. The extra code handles ownership transitions and verifies the restoration that upstream cannot promise for Acer.

## Installation handoff and removal order

1. Resolve repository coherence and GPU health; finalize running kernel/headers and recoverable stock boot.
2. Implement/build/test the narrow driver and integration package; pass disposable fixture/unit checks before installation.
3. Install daemon package inactive; install integration before first daemon start. Confirm actual installed version/unit match the reviewed candidate.
4. Complete driver telemetry, per-fan response, and Auto restoration qualification with CoolerControl stopped.
5. Start guarded CoolerControl without boot profile application; map sensors, create/configure profiles, apply under observation, export settings.
6. Prove stop, SIGKILL, watchdog-hang, source loss, all enabled sleep paths, restart and reboot behavior. Confirm curves persist with GUI closed and no login. Enable boot service and `apply_on_boot` only once appropriate tests pass; rerun final reboot acceptance.
7. Removal: stop/disable daemon while restoration helper is still installed; verify both modes2. Remove saved assignments/disable boot application or archive configuration. Remove controller integration and its sleep dependencies, then driver override according to driver rollback plan. Return to stock boot if necessary; verify stock ownership. Remove optional GUI/daemon packages only if no longer wanted. Never uninstall the helper before its final stop/restoration duty.

Unresolved facts are explicit hardware gates, not hidden design work: firmware command acceptance, stable minimum duties, exact curve points, valid NVIDIA telemetry, successful recovery time, and sensor behavior across GPU power states. Failure means firmware Auto remains the fallback and the failed gate gets focused investigation; it does not justify inventing temperature data or claiming temperature control works.
