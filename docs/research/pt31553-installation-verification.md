# PT315-53 staged installation verification and recovery

Research date: 2026-09-09. **A proposed execution procedure; no hardware stage has passed yet.** This investigation performed source/documentation reads and unprivileged machine inspection only. It did not build, install, load, unload, write fan controls, change services, or reboot.

## Decision

Use staged admission: verified stock recovery → matching module build → telemetry-only candidate → independent fan control and Auto restoration → CoolerControl temperature curves → lifecycle tests → persistent operation. Each stage needs observable results before the next. A firmware failure sends the work back to a focused protocol investigation; it does not justify enabling the daemon anyway.

The final delivery must control fans from **both CPU and GPU temperature**, start automatically without the GUI, and restore firmware ownership when software control stops. Manual fan settings below are short verification steps, not the delivered operating mode.

## Known machine facts and unresolved prerequisites

The existing map's machine snapshot records Acer Predator PT315-53, Civic_TLS, BIOS V1.17, CachyOS `7.2.2-1-cachyos`, stock `acer_wmi` loaded, and no fan/PWM hwmon endpoints. Parent-session discovery reports current headers, an installed LTS kernel, systemd-boot, and enabled UEFI Secure Boot. Recheck these at execution time. Secure Boot state alone does not answer whether this kernel will accept the candidate module; use the companion driver-installation investigation.

This session's `bootctl list --no-pager` failed because `/boot/loader/loader.conf` was unreadable. Therefore no selectable recovery entry was verified here. `fancontrol.service` exists and is disabled; that is not proof no other process controls fans. The parallel controller investigation also found NVIDIA temperature reporting `[GPU requires reset]`; restore valid GPU telemetry before accepting any GPU curve. A stock recovery reboot is a useful first opportunity to recheck that fault, not an assumed cure.

The companion investigations select a **version-specific pacman module override under `updates/pt31553`**, retaining the stock module, for the first installation; automatic DKMS rebuilding is deferred. They also found the local package database advertises CoolerControl 4.3.1 while the live package is 5.0.0, but the freshly inspected kernel mirror offers 7.1.8, older than installed 7.2.2; its LTS offering is older too. Refresh and review repository/package state on stock, then choose a coherent supported transaction before pinning/building the candidate. Do not force a kernel downgrade to match that mirror snapshot or blindly apply an upgrade. Preserve verified stock recovery. If an approved transaction changes kernel/headers, reboot and repeat the baseline. Resolve repository inconsistency before dependency-changing installation rather than create a partial-upgrade state.

## Driver facts that constrain the order

The examined CachyOS driver maps sysfs `pwmN_enable=2` to firmware Auto, `1` to Custom, and `0` to Turbo; `pwmN` is 0–255 converted to integer firmware percent. Expect rounding, not exact duty readback equality. The temperature/fan attributes depend on firmware sensor discovery. Profile initialization precedes hwmon initialization. The existing suspend, resume, remove, and shutdown callbacks do **not** restore fan Auto. Thus unloading the module is not a fan recovery operation, and a successful load alone proves little. [Exact driver source](https://github.com/CachyOS/linux/blob/11f0a985180e84707198334e5e612c24fa947f9c/drivers/platform/x86/acer-wmi.c)

Discover hwmon devices by their name and parent/device identity every time; never save an `hwmonN` index as identity. RPM and temperature channels are observations; a successful duty write is only a request. The ordinary hwmon interface documents integer text values and driver-specific attribute availability. [Linux hwmon ABI](https://docs.kernel.org/hwmon/sysfs-interface.html)

CoolerControl needs writable PWM for this laptop path. Profile support includes graph curves and mixing component demand; a visible read-only fan cannot satisfy the destination. The companion controller investigation selects exact package/configuration and recovery glue. [Laptop support](https://docs.coolercontrol.org/devices/laptops), [profiles](https://docs.coolercontrol.org/cooling/profiles)

## Ordered execution gates

**R** means observation only; **W** changes the installed system or hardware; **P** needs Danny physically at the laptop. A later execution session can perform routine privileged steps once available, but must not assume a working sudo credential, local terminal, or reboot recovery connection.

| Stage | Action, in order | Pass and failure branch |
|---|---|---|
| 1. Baseline and ownership (R) | Record DMI, BIOS, running kernel, package/header versions, installed/loaded module identity, Secure Boot/module admission facts, boot entries, current sleep mode, CPU/GPU temperatures and validity. Inventory system services, user services/autostarts, running fan tools, and loaded competing drivers. Save controller/config/module manifests before changing them. | Exact target confirmed; both component temperatures usable; all potential fan writers understood. If GPU is invalid, resolve telemetry before curves. If ownership is unclear, settle it before any PWM write. |
| 2. Recovery rehearsal and package-state review (W/P) | With candidate/controller still disabled, establish a stock LTS boot entry that excludes the custom module, including its initramfs. Save work. Danny actually selects and boots it from systemd-boot, verifies kernel, stock module, display/input/network needed for recovery. Refresh and review repository/package state; proceed only with a coherent supported transaction, retaining stock recovery and without a forced downgrade. Return to the intended kernel, repeat stage 1 after any kernel change, and recheck GPU telemetry. | A working recovery boot has been demonstrated, not merely listed. If it fails, repair it before candidate loading. If installed versions remain newer than repository offerings, resolve or explicitly account for that state before dependency-changing installation. Preserve recovery throughout; reverify it if its artifacts change. Prevent candidate packaging from automatically contaminating recovery. |
| 3. Candidate build (W, files only) | Follow companion packaging/signing plan. Build the telemetry-only patch first against the exact installed source/configuration/headers/symbols; keep the PWM patch separate. Record source, patch and artifact hashes, vermagic and signer/admission evidence. Review changes for exact DMI restriction and profile-coupling effects. | Build clean; artifact matches the intended kernel; candidate selection and stock restoration are understood. No force-load, symbol/version workaround, or broad DMI substitute if it fails. Correct the package/source/admission problem first. |
| 4. Telemetry admission (W/P, then R) | Stop known competing fan services using their own firmware restore path if needed. Load the reviewed telemetry candidate deliberately using the packaging plan; keep curve daemon disabled. Rediscover hwmon. Read both RPMs repeatedly and cross-check CPU/GPU temperatures against independent sources. Brief ordinary CPU and GPU activity can establish that values change. Check journal and basic Wi-Fi, brightness and hotkeys because this replaces a platform driver. | Both expected fan channels are present, readable and plausible under activity, with no new firmware errors/platform regressions. No PWM exposure is expected in this first stage. Missing hwmon may be profile setup failure or firmware sensor discovery failure: preserve logs and investigate the actual failure before adding PWM. |
| 5. PWM and recovery admission (W/P) | Replace telemetry candidate with the reviewed PWM candidate while no controller owns fans. Read both `pwmN`, `pwmN_enable`, and RPMs. Run the independent Auto-restore helper while the driver exists; it must write `2` and verify readback on **both** channels. Then make one brief controlled fan-mode transition and immediately restore Auto again. | Both channels have valid mode/duty reads and demonstrated return from Custom to Auto. If Auto cannot be established, stop before temperature-load tests, follow recovery below, and open the protocol decision. Merely writing Auto when already Auto is insufficient final proof. |
| 6. Independent response (W/P) | At idle, test one fan at a time; keep the other in verified Auto. Use two distinct moderate-to-high requests chosen conservatively during execution, observe requested duty/mode and resulting RPM settling, restore Auto, then repeat for the other channel. Establish a working nonzero floor without a fan-stop calibration sweep. | Changing channel A produces a repeatable intended fan response; channel B likewise. Allow firmware rounding and ordinary RPM variation. Unexpected coupling, zero/error/stuck RPM, unexplained reversions, or ineffective duty requests fail the gate. Do not infer physical CPU/GPU labels solely from numbering; record the verified mapping. |
| 7. Controller installation and first start (W/P) | Install the chosen CoolerControl package and reviewed recovery integration with automatic start initially disabled. If package download/install is done earlier with the reviewed stock package transaction, inspect its hooks/presets and keep the daemon inhibited before any candidate hardware test. Establish Auto on both fans before first daemon initialization. Confirm only one writer; identify stable CPU/GPU sensors and both laptop fan channels. Set conservative graph curves with a validated floor, a full-demand upper section and controlled down-ramping. Have both fans honor the greater CPU/GPU cooling demand if using the selected mixed-demand design. | Saved configuration uses actual valid sensors/channels and survives daemon restart; readings are fresh and errors observable. If GPU disappears, CPU-only success does not pass. Do not accept guessed sensor UIDs, guessed curve endpoints, or config for another release. |
| 8. Temperature response (W/P) | With logging and restoration ready, use short CPU-only, GPU-dominant, then mixed ordinary workloads. Start with light load and cross curve segments; stop each workload and observe cooling. Prefer existing user workloads; choose any dedicated load command explicitly with a bounded duration before running it. | Each component can independently raise demanded duty, and actual RPM follows; demand decreases stably after cooling. No sustained conflict with firmware, unexplained fan stop, thermal alarm or rising heat without response. If thresholds cannot be crossed comfortably, temporarily put test breakpoints in the observed normal temperature range, then restore intended settings; do not overheat merely to test an upper curve point. |
| 9. Failure and lifecycle acceptance (W/P) | Run the matrix below at idle first. Keep recovery shell/helper ready and candidate module loaded. | Every applicable result is observed. A failed recovery/ownership/sensor-loss test blocks unattended startup, even if normal curves look correct. Fix only the missing integration and repeat the failed case plus affected normal operation. |

## Lifecycle acceptance matrix

Run disruptive cases with Danny present, no sustained load, and valid telemetry. Inspect real state after each action, then repeat a small temperature response after recovery.

| Case | Required observation |
|---|---|
| Graceful service stop | Daemon stops; both mode readbacks become `2`; no process resumes writes afterward. Restart begins from Auto and fresh sensors. |
| Unexpected process exit | Deliberately terminate the daemon without graceful cleanup during the supervised test. Independent service cleanup restores **both** channels and reports results before any automatic restart can claim them. A restart that hides a failed reset is a failure. |
| Missing/error sensor | Using the actual controller's supported test mechanism or a controlled test fixture, cause each chosen component source to become unavailable. Demand must not drop as though temperature were zero. Prove either the selected release's protective high-demand path followed by recovery, or verified Auto restoration. Avoid unloading the GPU driver as a casual fault injection. |
| Controller stops making progress | Verify the installed unit's existing watchdog trips when the daemon stops completing its loop, then invokes independent cleanup and preserves verified Auto before restart. The companion audit found 5.0.0 already supplies `Type=notify`, `WatchdogSec=30` and completed-loop heartbeats; use it rather than add another watchdog. Record the measured delay and recovery. A live PID is insufficient. |
| Write/reset failure | Test helper/guard error branches with fake files or injected command failures, not by removing the live driver during Custom mode. Startup/restart is refused; failure is visible; no successful-reset message is emitted. Hardware Auto refusal itself follows the emergency branch below. |
| Suspend and resume | Before sleep, daemon is quiescent and both fans have logged Auto readback. After wake, rediscover device paths and require fresh CPU/GPU data before reapplying curves. Verify the configured sleep mode and normal lid action. If hibernation/hybrid sleep is enabled and used, exercise those paths too; otherwise record them as not accepted. |
| Reboot/shutdown | Verify service restoration occurs while sysfs still exists, before device teardown. On next boot, no stale Custom baseline is accepted; sensors and curves recover without GUI/login. A normal reboot test cannot establish behavior during a kernel panic or power loss. |
| GPU runtime sleep/wake, AC/battery, supported hotkey use | If part of ordinary use, verify these do not silently change channel ownership or invalidate a sensor while leaving reduced demand. A sleeping GPU is not automatically a failed cold sensor; the selected controller policy must cover wake before heat demand grows. |

`ExecStopPost=` is the appropriate independent cleanup phase for service failure/startup-failure paths; `ExecStop=` alone is insufficient. Its inclusion does not prove its writes succeeded. [systemd service documentation source](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml)

The companion controller integration defines `/usr/lib/pt31553-fan-control/session`: an `ExecCondition` sleep/fault guard, `ExecStartPre` Auto restoration plus fresh-sensor admission, and `ExecStopPost` verified restoration with a fault latch. Its sleep preparation must be required and ordered before the four systemd sleep engines; failure must block sleep, and resume restarts only a previously active daemon after fresh-sensor checks. Verify the generated unit dependencies and actual installed 5.0.0 watchdog settings before exercising the matrix. This is an implementation contract; the helper is not installed or tested by this research.

Sleep hooks execute around sleep, but user sessions are frozen and hook ordering is not a substitute for an explicit ordered service design. Kernel sleep states suspend userspace, so a curve daemon cannot continue controlling normally throughout sleep. [systemd sleep documentation source](https://github.com/systemd/systemd/blob/main/man/systemd-suspend.service.xml), [Linux sleep states](https://docs.kernel.org/admin-guide/pm/sleep-states.html)

## Recovery and uninstall, in the correct order

**Responsive driver/OS:** stop test workloads; stop the sole curve writer and prevent its restart; invoke the independent helper while the candidate remains loaded. Rediscover the intended Acer device, write Auto to each existing expected channel, and read both modes back as `2`. Check temperatures/RPM are settling. Only then disable/remove controller integration and remove/replace the custom module. Never treat `rmmod`, a disappeared sysfs directory, or a successful service stop as proof firmware control returned.

**Auto write/readback fails but the system responds:** stop workloads and automatic retries, retain diagnostic evidence if readily available, and do not run more load tests. An already-proven high-demand operation may be a temporary attended bridge to shutdown, not a substitute for successful restoration. Shut down promptly if cooling is uncertain. Boot the verified stock recovery entry and check ordinary fan behavior/temperatures before returning to work. A warm reboot or power-off is not claimed to reset this particular EC; persistent abnormal cooling requires model-specific recovery investigation, not repeated blind commands.

**OS/firmware unresponsive or fan behavior unsafe:** userspace helpers cannot guarantee recovery. Danny must stop the experiment physically and power down if normal shutdown cannot proceed. Follow documented machine recovery only; do not invent battery-disconnect/EC-reset sequences. Do not keep the machine running a workload while waiting for a hung WMI request.

**Planned uninstall:** stop load → stop daemon and verify Auto → disable its startup/recovery units → remove only this candidate package and introduced module-selection/boot configuration → regenerate module dependencies and affected initramfs through the chosen package mechanism → verify stock module resolves for affected kernels → boot stock → verify baseline behavior. Keep the restoration helper/module until the Auto step succeeds. Retain unrelated packages, boot entries and signing keys. Restoring firmware control is the first operation; package cleanup is the last.

## Small evidence bundle and final acceptance

Keep one session log plus saved config/package manifest. For each test record time, action, CPU/GPU source values, requested duties, both mode readbacks, both RPMs, controller state and relevant kernel/service errors. A simple CSV sampled at the controller interval plus journal excerpts is enough. Capture before/during/after values; no serial numbers, full environment dumps or new qualification registry are needed.

Choose thermal stop thresholds from this machine's exposed hardware limits and documented component limits, with headroom, during execution. Choose duty floor from observed fan operation. Neither a universal temperature ceiling nor guessed RPM percentages is established by these sources. Stop an experiment if heat rises without the expected response, a required sensor becomes invalid, a fan unexpectedly stops, or a hardware thermal warning appears. Do not intentionally reach critical temperatures or rely on thermal throttling to validate a curve.

Completion means: exact model proven; known-good stock recovery; both fan channels controllable and recoverable; CPU and GPU independently drive temperature demand; graceful and abnormal stop recover; configured sleep and reboot restore operation; updates have a defined stock fallback; and uninstall has an ordered reversible path. Firmware compatibility, exact curve values and hardware stage results remain measurements for the execution session, not research findings.
